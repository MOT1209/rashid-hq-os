# Migrations

كيف تُطبَّق ترحيلات قاعدة البيانات على Supabase بأمان — بدون لوحة SQL، ومن سطر أوامر واحد.

الأداة: `scripts/migrate.mjs`. الاتصال: `DATABASE_URL` من `.env.local` (نفس سلسلة الاتصال التي يستخدمها `auth-migrate.mjs`).

## الحالة الراهنة (2026-09-27)

- `0001..0013` مطبَّقة على الإنتاج **يدوياً سابقاً** (قبل وجود سجل ترحيلات).
- `0014..0020` **معلّقة** — تُطبَّق جميعها في دفعة واحدة بالأمر أدناه.
- لا جدول `schema_migrations` في الإنتاج بعد؛ الأداة تنشئه (بعد أخذ backup) ويسجّل فيه ما نُفِّذ فعلاً.

## الأوامر

```bash
npm run migrate:status     # ما هو مطبَّق وما هو معلّق (قراءة فقط، لا ينشئ شيئاً)
npm run migrate:dry-run    # معاينة ما سينفَّذ: رؤوس الملفات وفوائدها (قراءة فقط)
npm run migrate:apply      # backup ← تنفيذ دفعة واحدة ← validation
npm run migrate:baseline   # (مرة واحدة فقط) تسجيل 0001..0013 كمطبَّقة دون تشغيلها
```

> `baseline` ليس ضرورياً للترحيلات المعلّقة الحالية (الأداة تتجاهل ما هو ≤ 0013
> تلقائياً)، لكنه يوثّق الواقع في السجل ويجعل `status` صادقاً بالكامل. شغّله
> **قبل** `apply` إن أردت سجلاً كاملاً، وبعده إن كنت مستعجلاً.

## التطبيق (الإجراء الكامل)

```bash
# 1. تأكد أن DATABASE_URL موجود في .env.local وأنه يشير إلى الإنتاج
npm run migrate:status

# 2. اقرأ ما سينفَّذ قبل تنفيذه — الأداة لا تعمى أبداً
npm run migrate:dry-run

# 3. نفّذ
npm run migrate:apply
```

ما يفعله `apply` بالترتيب:

1. **قفل استشاري** (`pg_try_advisory_lock`) — لا تشغيلان متزامنان أبداً.
2. **Backup** لكل جداول `public` إلى `backups/pre-migrate-<stamp>.json`
   (+ `.manifest.json` بعدّ الصفوف لكل جدول). فشل الـ backup يوقف كل شيء قبل
   لمس المخطط.
3. **تنفيذ الملفات المعلّقة بالترتيب الرقمي داخل معاملة واحدة** — أي فشل يُرجع
   الدفعة كلها: قاعدة البيانات تبقى كما كانت تماماً.
4. **Validation بعد الالتزام** — استعلامات تتحقق من الكائنات التي كان كل ملف
   يفترض أن ينشئها (أعمدة، قيود، جداول، فهارس، صفوف seed). أي نتيجة `false`
   توقف العملية بخطأ واضح.
5. تسجيل كل ملف في جدول `schema_migrations`.

## Rollback

بترتيب الأقل تكلفة أولاً:

1. **الملفات قابلة لإعادة التشغيل بالتصميم** (`create if not exists`، إضافة
   أعمدة محمية بـ `if not exists`): احذف صف الملف المسبِّب من
   `schema_migrations` ثم أعد `migrate:apply` بعد الإصلاح.
2. **استرجاع بيانات**: ملف الـ backup JSON كامل — `backups/pre-migrate-*.json`.
   الجداول الجديدة (0015/0016/0017/0018/0020) تبدأ فارغة أصلاً فلا تحتاج
   استرجاعاً عادةً؛ إن لزم، `delete` من الجدول المسبِّب ثم أعد التطبيق.
3. **التراجع عن 0014 تحديداً** (تغيير قيد على جدول موجود): أعِد القيد القديم
   `check (status in ('success','failed','pending'))` من لوحة Supabase SQL،
   واحذف صف `0014_policy_decisions.sql` من السجل. الأعمدة المضافة تبقى لكنها
   لا تضر (الكود القديم يكتب فيها `null`).

## التحقق اليدوي بعد التطبيق (من plan.md §5)

| ماذا | المتوقّع |
|---|---|
| توكن كتابة → `delete_project` عبر `/api/mcp` | «بانتظار الموافقة»، لا حذف؛ يظهر في `/dashboard/access` |
| موافقة مشرف على الطلب | الحذف يقع فعلًا، السجل → `success` |
| رفض طلب آخر | المشروع يبقى، السجل → `failed` |
| عطّل `delete-project-needs-approval` من لوحة السياسات ثم أعد تفعيلها | الحذف يُنفَّذ فوراً عند التعطيل ويعود للطابور عند التفعيل |
| طلب حذف ثم شدّد قاعدة ثم وافق | يُحظر بدل التنفيذ (إعادة تقييم وقت الموافقة) |
| محادثة كونسول + تفويض حقيقي | صفوف في `agent_runs` بـ`kind` صحيح وتوكنات غير صفرية |
| اضبط سقفاً صغيراً لقسم | تجاوز 80% يصلك بريد واحد؛ عند 100% التفويض يُرفض |
| فتح `/dashboard/insights` | الأرقام تطابق ما في `agent_runs` |

## قواعد عند إضافة ترحيل جديد

1. اسم الملف: `NNNN_وصف_قصير.sql` بترتيب رقمي متصاعد.
2. **قابل لإعادة التشغيل إجبارياً**: `create table if not exists`،
   `add column if not exists`، `on conflict do nothing`، وحماية أي `drop`/قيد
   بفحص `pg_constraint`/`pg_class`.
3. أضف استعلامات validation له في `CHECKS` داخل `scripts/migrate.mjs`.
4. RLS مفعّل + `revoke all from anon, authenticated` لأي جدول جديد (نمط 0013+).
5. حدّث هذا الملف وقسم «الحالة الراهنة».
