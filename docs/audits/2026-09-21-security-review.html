  • مفتاح service-role لا يغادر السيرفر إطلاقًا؛ تحديد معدل تسجيل الدخول في Postgres (يصمد أمام تعدد النسخ).

المتوسطة — التفاصيل

M1 — حقن HTML في رسائل البريدمتوسط · قابل للاستغلال اليوم

القيم المعروضة في القوالب تُدرج دون تهريب: sendHealthAlert (email.ts:100,104,107,109) يدرج project.name وendpoint وrun.department؛ sendStandingTaskDigest (email.ts:147-150) يدرج run.department وrun.summary (نص LLM من تشغيل غير مراقب)؛ sendPasswordReset (email.ts:199-210) يدرج الـ URL.

run.summary يولّده الوكيل نفسه تلقائيًا — أي نص خرج إليه وكيل إدارة يتسرب إلى قارئ البريد معرّى. الأثر: XSS في عميل بريد HTML وتزوير محتوى/روابط.

الإصلاح: دالة escapeHtml موحدة تُطبَّق على كل تحقين في قوالب HTML + اختبار وحدة للتهريب (لا يوجد اليوم).

M2 — الـ dedup للويبوکس غير مربوط بالمحتوى الموقَّعمتوسط

توقيع github.ts:119-133 يغطي الجسم فقط عبر HMAC، أما event_id فيأتي من ترويسة X-GitHub-Delivery غير الموقّعة. تُدرج الصفوف بـ (route.ts:61-79) وتُعالج 23505 كإعادة؛ لكن event_id: verdict.eventId ?? null (السطر 63): بلا ترويسة يصير NULL، وفي Postgres NULL ≠ NULL تحت الفهرسة الفريدة — فيُمرَّر كل تكرار.

الأثر اليوم ضئيل (صف واحد يُضاف، المعالجة الفعلية غير مفعّلة)، لكنه يحكم كل معالجة قادمة. الإصلاح قبل تفعيل معالجة الأحداث: مفتاح dedup مشتق من المحتوى الموقَّع نفسه (HMAC من rawBody) + معالجة صريحة لـ NULL.

M3 — مخطط مفتاح تعمية التكاملاتمتوسط

encryption.ts:27-36 يشتق المفتاح بـ createHMACKey('SHA-256', secret) مباشرة — بلا KDF/ملح/نسخة مفتاح. بلا KDF، أي سر منخفض الإنتروبي ينعكس لمفتاح قابل للـ brute-force. وبلا key_id، تغيير INTEGRATIONS_SECRET يكسّر كل الاتصالات المخزنة (التدوير = فقدان).

الإصلاح: HKDF/scrypt بملح مشتق + عمود key_id في integration_connections، وتوثيق أن السر يُولَّد بـ openssl rand -base64 32.

ثغرات التغطية (الأهم أولًا)

  • لا اختبار لعقد تقرير runTool (executor) — لا شيء يؤكد أن كل قرار (deny / awaiting / allow) يكتب agent_logs بالقرار وactor_type الصحيحين.
  • لا اختبارات لسطح /api/mcp (parse/defat/oversize/notifications) ولا mcp-server — إلا mcp-route-ping.
  • لا اختبارات لمسارات الويبوکس والـ OAuth — verifyWebhook مُختبَر كدالة، لكن الـ route كاملةً (حمولة، توقيع فاسد، مكرر، 404) و callback/connect (state، انتهاء، redirectTo) بلا تغطية.
  • لا اختبار لـ proxy rate-limit (clientIp / overLimitInMemory / windows).
  • snapshot tool-schemas يفلت منه أي أداة جديدة بصمت — أدخله المراجعة الذهنية.
  • إلغاء التقلب في members.test.ts وtoken-hashing.test.ts (رفع المهلة/زمن وهمي).

الخلاصة

بنية أمنية جيدة: حراسة SSRF وتوکنات مجزأة وCSP صارم وأدوار — ولا ثغرة حرجة أو عالية في الكود المُفحص. لكن خط الإنتاج مكسور في اللحظة الحالية (أنواع Supabase لم تُحدَّث بعد 0017) وقاعدة الإنتاج معلقة الترحيلات — وهاتان نقطا البداية فعلًا. بعدها تأتي M1 ثم M2 ثم M3. الإطار العام: أمن جيد، انضباط توثيقي يحتاج استعادة، واختبارات جيدة الحجم تحتاج خياطة في النقاط الحاسمة.
